# Architecture overview

[← Back to README](../README.md)

How TS Media chat is put together: the modules, the link format it posts, how uploads and downloads flow, how copies of the plugin talk to each other, and the rules that keep it safe inside TeamSpeak's process. For build instructions, see [building from source](BUILDING.md); for the updater, see [updates](UPDATES.md).

## Platform constraints

- The plugin is a DLL loaded into the TeamSpeak 3 client (plugin API 26). It uses the Qt 5.15.2 that TeamSpeak 3.6 ships, and only the modules TeamSpeak ships with it: QtCore, QtGui and QtWidgets. There is no QtMultimedia and no QtConcurrent.
- Video, audio, voice recording and video compression use Windows Media Foundation and WASAPI directly. `mfplat.dll` and `mfreadwrite.dll` are delay-loaded and checked for before use, so the plugin still loads on Windows N editions without the Media Feature Pack, just without those features.
- SHA-256 checks (and the signature checks of the old update manifest and of the important-update marker) use Windows CNG (`bcrypt.dll`). `winhttp.dll` (and `ws2_32.dll` for link previews) is loaded on demand, never imported: in official builds while an update check or download runs, and in every build for a link preview's website request (2.4).
- The previews live inside TeamSpeak's own chat: TeamSpeak's chat views are `QTextBrowser` widgets, and the plugin adds its previews to their documents as image resources placed under the file links.

## Link and message format

A sent file is posted as the same kind of BBCode link TeamSpeak itself creates when a file is dragged from the file browser into the chat:

```text
[URL=ts3file://<host>?port=..&serverUID=..&channel=..&path=..&filename=..&isDir=0&size=..&fileDateTime=..&tsm=2&w=..&h=..&d=..&bh=..&pv=..]<file name>[/URL]
```

TeamSpeak ignores the extra parameters, so clients without the plugin can still click the link and download the file. TS Media chat adds only the ones that apply, all percent-encoded:

| Parameter | Meaning |
| --- | --- |
| `tsm` | marks a TS Media message (current protocol: 2) |
| `w`, `h` | media size in pixels, in display orientation |
| `d` | duration in milliseconds (video and audio) |
| `bh` | BlurHash placeholder |
| `pv` | path of a small JPEG preview or video poster in the same channel (2.2: `<dir>/previews/<8 hex>.jpg`) |

2.2 adds these after `pv`, always in this order and only on links with `tsm` 2 or higher. Their values are base64url (no padding), hex or plain numbers, so they are never percent-encoded:

| Parameter | Meaning | Accepted only if |
| --- | --- | --- |
| `sha` | SHA-256 of the file | 43 characters, canonical last character, decodes to 32 bytes |
| `ph` | first 16 bytes of the preview's SHA-256 | 22 characters, canonical, and the link has a valid `pv` |
| `sp` | spoiler | exactly `1`, on a picture, GIF or video |
| `al`, `ai`, `an` | album id, position, size | `al` is 8 lower-case hex digits and not `00000000`, `an` is 2–10, `ai` is 1–`an`; all three or none |
| `vm` | voice message | exactly `1`, on an audio file |
| `wf` | waveform of a voice message | only with `vm`: 64 levels of 4 bits = 32 bytes, 43 characters, canonical |

- Parsing accepts plain TeamSpeak links (no `tsm`), unknown parameters, any parameter order and HTML-escaped ampersands. The first occurrence of a parameter wins, and an invalid value drops only that field (the album: all three), never the link. A link without the 2.2 fields is byte-identical to what 2.1 sent.
- The key that identifies a file (cache names, chat resources, reactions) is the first 20 hex digits of SHA-1 over `serverUID`, channel, remote path and size, joined by `\n`. When the link carries a `sha`, `\n` and its base64url text are appended, so a link with a forged hash can never share the genuine file's entry. Links without one keep 2.1's key. This definition is frozen: every 2.2+ client computes the same key from the same link.
- A tag escaped with a backslash (`\[URL=…`) or broken by an invisible character (`[` U+200B `URL=…`) is text in TeamSpeak's chat, so it is never taken for a link either. `[noparse]` protects nothing: TeamSpeak 3.6 drops the tags and still parses what is inside, so the plugin never uses it.

A message is `[caption]` + LINK (+ LINK…) + `[note]`, the parts separated by a line break (`kMessageSeparator`):

- The caption comes first, because 2.1 receivers remove the text after a TS Media link. It is one line of at most 300 characters, without control or bidirectional-text characters; every `[` and `]` gets a backslash before it (TeamSpeak then shows the bracket as text), so a caption can never open a tag or fake a file link. Web addresses need no `[URL]`: the chat links them itself. The plugin's own chat lines (`printInfo`, `printWarning`) escape names the same way.
- Each link's label is the file's display name without the random part, `Spoiler (image)` / `Spoiler (GIF)` / `Spoiler (video)` for spoilers, or `Voice message (0:12)`.
- When the note for people without the plugin is on, it follows the last link of the first message, once: a grey, italic *— TS Media chat plugin required to view this in chat*, with "TS Media chat" linked to the configured download page.
- Several links share a message while they fit (albums). TeamSpeak takes up to 8192 UTF-8 bytes of text, and its client silently drops a command whose escaped form (ServerQuery escaping: `\`, `/`, space, `|` and control characters take two bytes) is above about 9.1 KB. Every message therefore keeps its escaped size (`escapedMessageSize()`) at or below `kMaxMessageBytes` = 8168; a 10-item album fits in one message. When a link doesn't fit, optional data is dropped in one order: `ph`, `bh`, `wf`, the note's link, then the caption moves to a message of its own right above the files, then the note, `pv`, `w`/`h`/`d` and `sha`. TeamSpeak's own parameters, `tsm`, `sp`, the album and `vm` are never dropped, the caption is never cut, and links are never stripped just to fit more of them into one message.
- Clients with the plugin remove everything after a TS Media link up to the next link or the end of its line, so they never see the note.

## Sending

1. **Validate and stage.** The plugin checks that the client is connected, that the file is not empty and within the upload limit (the server's own limit when it has one), and that the channel has no password. It then stages a copy of the file, named as it will be on the server, in the plugin's data folder. The copy is made on a worker thread, so a large file never blocks the chat. Edited pictures are exported by the send window first and staged like any file; voice messages arrive as a finished `.m4a`.
2. **Probe.** On a worker thread it reads the size, duration and BlurHash of the staged copy, and makes a preview or poster when the file needs one.
3. **Compress (videos).** A video that may be compressed is probed where it is instead, before any copy, and `videocompress::planCompression` decides with a snapshot of the settings taken when the send started (the send window's Quality list asks the same planner). To compress, the job is `UploadState::Compressing`: one video at a time on Core's transcode pool, below normal priority. `mf::transcodeToMp4` reads the original with a Source Reader (scaled, rotated upright and converted by the reader), writes H.264 High and AAC-LC with a Sink Writer, tries the graphics card first and the processor once, and verifies the result (opens, size, upright, sound, length). The verified MP4 is moved into staging with the same random part in its name. If it fails and the original fits the upload limit, the original is staged and sent instead.
4. **Hash.** One step, `finalizeStaged`, hashes the final staged bytes (after an edit's export or a transcode's verification) and the preview, off the GUI thread. A file that can't be read is sent without `sha`, and the log says so.
5. **Prepare folders.** It makes sure the upload folder and its `previews` folder exist. Without permission to create folders, the file goes to the channel root; if only the previews folder fails, the preview goes next to the file as `<8 hex>.preview.jpg`. Remote names are `<base>_<8 hex>.<ext>`, the base cut to 48 characters and 64 UTF-8 bytes.
6. **Upload the preview, then the file.** A failed preview is not fatal: the file is sent without it. At most two files upload at once.
7. **Wait for the server to have all of it** (2.3.2, `uploadwait.h`). TeamSpeak reports an upload complete once the last bytes are in its socket; on a real internet link part of the file is still on its way, and while it arrives the server reports only the bytes it has so far. So the file's message waits: Core asks the server for the file's size (`requestFileInfo`) right away and again after 300 ms, backing off to every 2 s (each question through the `FloodGovernor`, below), until it reports the whole size. Only servers that look like TeamSpeak's own are asked (2.3.3, `uploadwait::canAskFileInfo`): TeaSpeak answers `requestFileInfo` with a notification the TeamSpeak client can't parse, and the client drops the connection. Any other server counts as one that can't tell, without a question: its bytes decide (below). The preview went out before the file, so it is asked about only when the file itself wasn't all there at the first question (one question per file otherwise, so an album's message isn't held back by flood points). The toast says *Posting to chat…* meanwhile and the upload can still be canceled. Without a confirmation after 60 s without growth (or 60 s plus the file at 100 KB/s), or when the server can't be asked (no such file), the message goes anyway, with a warning in the log. A lost connection meanwhile fails the message like any other that couldn't go: the file stays on the server, and Retry asks the server again and then posts the message, without a second upload.

   **Then its bytes.** A server that preallocates uploads (TeaSpeak, as seen on Linux) reports the whole size from the start and has zeros where the bytes haven't arrived yet, so the size alone can pass too early. Once the size is right (or the server can't tell it, for example without permission to look at files), Core reads the end of the server's copy back and compares it with the end of what was uploaded: the last 64 KB of the file's data and any zeros after them (`uploadwait::tailWindow`; the bytes arrive in order and the server's zeros are there from the start, so the window has to reach the file's last non-zero byte, up to 1 MB back; a file that is all zeros, or ends in more of them, has no window), downloaded with TeamSpeak's resume (a sparse local file of the size minus the window in `<data>/servercheck/`, so the gap is never written to disk, then `requestFile` with resume, so only the end comes). The uploaded end is read from the staged file (or the cache copy) when the upload completes and kept in memory with the check, so a Retry after a lost connection still has it. Equal: the message goes (the log says `Server has all of … (content checked: tail) after … ms`). More zeros at the end than uploaded, or fewer bytes than asked for (still arriving): checked again after 0.5, 1, 2, 3, 5 and then every 8 s, within the same limits (the deadline above, and 60 s in which what the server shows doesn't change), then the message goes anyway with a warning. A tail that comes back too long or empty (a server that can't send the end alone), one of the right length with other bytes than zeros (the resume's offset ignored), or a download that fails: the whole file is downloaded (up to 16 MB, with `sha`) and its SHA-256, computed on a worker thread of the checks' own, compared with the link's (`content checked: full`); larger files, or files without `sha`, go after the size check (`content check not possible`, `size only`). A check refused for lack of permission goes after the size check at once, and later files in that channel aren't checked by their bytes until the connection ends. The preview is checked the same way when it is asked about at all (above, and also when the file's own bytes weren't all there at once). A check's download that doesn't finish within 20 s (plus the file at 100 KB/s for a whole one) counts as other bytes. Checks count as downloads (one slot each; with all slots taken, one check at a time still goes) and as transfers on the `FloodGovernor`; canceling the upload (its check is halted before the file is deleted), a lost connection (tab closed) or plugin shutdown halts a check's download and removes its folder (folders TeamSpeak still held go with the next check), and `<data>/servercheck/` is cleared at start. Nothing here depends on recognising the server: the official server simply passes at the first check.
8. **Post the messages** to the chat the user is looking at (channel, server or private chat). Every send goes through `Core::send(SendRequest)`: the albums first (pictures and videos, up to 10 each, posted once all of their files are uploaded, failed or canceled; the files that made it are numbered again), then the other files in their order, with the caption on the first message (a reply's quote line goes right before the caption, in the same message). Each connection has one post queue and one `FloodGovernor`, which models the server's anti-flood counters as measured (defaults: 150 points, 5 points back per second; a chat message costs 15, file info 8, a folder 5, a transfer 3; plugin commands cost 5 on a counter of their own). Messages go one at a time, each after the answer to the previous one or a second (the messages of one send wait for that answer, or its 5 s timeout, so they always arrive in order), and only while 30 points stay free for the user's own typing: from rest about 8 messages back to back, then one every 3 s. Folder requests and upload starts wait for the same governor and leave room for one more message, so a large album never runs into the limit; each folder is asked for once per connection, and a flooded folder or upload request is sent again after the pause instead of failing. After a flood error (`0x020c`) everything pauses for the server's `retry in <n>ms` plus 250 ms, then exactly one message goes and the steady rate follows; a flooded message is sent again up to three times. A message without any answer within 5 s is never counted as sent: it fails, and Retry posts the same message again (the files are not uploaded twice).
9. **Seed the cache** with the file and its preview, so the sender sees their own upload at once. Text taken from the chat input as the caption is removed from it only once the caption was posted (`Core::captionSettled`).

## Receiving

- Every TS Media link and plain TeamSpeak file link in the chat gets an entry with sanitised metadata. Entries move through the states *Idle*, *Queued*, *Downloading*, *Ready* and *Failed*.
- Previews and posters download automatically. Images, GIFs and voice messages (at most 16 MB) download automatically up to the configured size; videos and audio files only up to their own limit, which by default means only when the user presses play. Data saver (for all servers or per server) holds every automatic download except previews, and covered spoilers wait for their reveal.
- At most three transfers run at once; previews go before main files. Downloads interrupted by a lost connection are retried once the server is reachable again.
- **Verification.** Once TeamSpeak has closed a downloaded file, a link with `sha` is hashed on the verifier's own threads. A mismatch is checked once more (TeamSpeak may report a transfer complete before the bytes are on disk); if it still differs, the file is deleted and never shown. A preview whose `ph` doesn't match is not shown.
- **Waiting for the sender's upload** (2.3.2, `uploadwait.h`). A download that came out shorter than its link says, or didn't match its `sha`, may have raced the sender's upload (older senders post as soon as TeamSpeak reports the upload complete). Instead of failing, the entry stays *Downloading* (*Waiting for the sender's upload…*, with the waiting glyph instead of a percentage) and Core asks the server for the file's size (2.3.3: only a server that looks like TeamSpeak's own; any other one counts as one that can't tell, see below; questions and downloads both wait for room on the `FloodGovernor`; a question without an answer, for example held back by the flood protection, is asked again before the server counts as one that can't tell): while it is still short, again after 2, 4, 8, 15 and then every 30 s, as long as it keeps growing (three minutes without growth and it fails, *Download failed*, with Retry, and the size it stopped at counts as the file's real one, so other links naming another size aren't fetched automatically); once the server has the whole file, the file is downloaded again, each attempt in a partial folder of its own. A mismatch is final once a download started after the server reported the whole file gives the same wrong digest as the one before it: *File doesn't match what was sent*, and only then is that digest remembered for the forged-hash guard. When the server can't tell (no permission to look at files), downloads decide: two in a row that bring nothing new end it (too short: *Download failed*; the same wrong digest: *File doesn't match what was sent*, never remembered). An automatic download stays one while it waits: data saver turned on meanwhile holds it, and the automatic rules decide again before it is fetched; a click on it makes it the user's. A click on a file that didn't match still tries again: the forged-hash guard lets that one attempt through without forgetting what it knows. A file gone from the server fails as *File is no longer on the server*.
- **Zero tails** (2.3.2, `uploadwait.h`). On a server that preallocates uploads (TeaSpeak) a racing download is complete in size but ends in zeros where the bytes hadn't arrived. A complete download that doesn't match its `sha` and ends in a run of at least 512 zeros (a mismatch already shows it isn't the uploaded file, so a short run is enough, for small voice messages too), or one of a TS Media link without `sha` but with a size that ends in at least 4 KB of zeros (64 KB for videos and audio files), is such an upload still arriving, never a mismatch: where its data ends is found on the verifier's threads (`fileverify::Verifier`, `uploadwait::dataEnd`), the entry waits as above (*Waiting for the sender's upload…*), and since that server's size says nothing, the file is downloaded again after 2, 4, 8 … s with the length of the data before the zeros as the progress. Downloads that bring no more data end it once nothing grew for 25 s (four of them, 2, 4, 8 and 15 s apart; or three minutes without more), as *Download failed* (*The file never arrived completely on the server*), with Retry, and no size is noted: the bytes before the zeros may stand still for a while (an older sender's last bytes on a slow line), and any growth starts the 25 s over. When the last of them had the same digest as the one before while the server reported the whole file, that digest is the server file's now: it is remembered for the forged-hash guard (so a file padded with zeros on purpose can't make everyone download it five times for every link with a made-up hash), and a click on the entry still downloads it once. Without `sha` nothing contradicts the file: once two more downloads bring no more data, the zeros are its own end (a WAV's silence, a tar's padding) and it is stored as it is. A file whose real end is zeros and whose `sha` matches is never affected (the check passes first).
- **Which server.** Once per connection the log says which server it is (`Server: 3.13.7 [Build: …] on Linux`, or `Server: TeaSpeak … on Linux (looks like TeaSpeak …)`), and the diagnostic info's *File checks* section lists the connected servers' versions with its counts of content checks and zero tails. That is for reading logs only: the logic above is the same on every server.
- The image shown for an entry is the best one available: the decoded file, then the preview or poster, then the BlurHash placeholder. Videos have no decoded still: they show their poster or placeholder until they play.
- **Albums.** Links with the same `al` from the same sender are grouped into one grid object, anchored after the first member's link. The other members' links are folded away, and follow-up messages that hold nothing but album links (and the note) are hidden with `QTextBlock::setVisible`. Turning previews off, disabling or unloading the plugin restores every folded link and hidden block. The sender's own albums are recorded at post time, so they group without depending on TeamSpeak echoing the sender's identity.
- Downloads go into a cache under `<data>/cache/<server hash>/<channel>/`. When the cache grows beyond its limit, the least recently used files are deleted, except media that is playing or open in the viewer. Dragged-out files are hard links (or copies) in `<data>/export/`, marked with a `Zone.Identifier` stream and removed after 24 hours.

## Between plugins

Copies of TS Media chat 2.2 talk to each other with TeamSpeak plugin commands (`sendPluginCommand` / `onPluginCommandEvent`). Receivers see the plugin name `tsmedia`, the DLL name without its architecture suffix.

```text
command = "tsm1" SP type *(SP key "=" value)      ASCII only, at most 32 tokens
HELLO pv=1 v=2.2.0 caps=p,r,l rr=1                I'm here (to the channel, or to one private-chat partner)
                                                  2.4: caps l = I make link previews; a caps change goes out as one HELLO rr=0
HI    pv=1 v=2.2.0 caps=p,r,l                     the answer, only to whoever asked
BYE                                               presence switched off, or the plugin unloads
R     s=c|p [y=1] i=<key>:<codes>,... [e=<key>:<emoji>.<emoji>,...]
                                                  my complete reaction set on each media item (idempotent)
SYNC  s=c m=<key>,...                             a late joiner asks present members for their own reactions
TR    s=c|p [y=1] i=<hash>-<age>:<codes>,... [e=...] 2.3: the same for messages without media
TSYNC s=c m=<hash>-<age>,...                      2.3: the same as SYNC for those messages
LP    s=c|p m=<hash>-<age> u=<url key> k=y|i|g|v c=<channel> p=<path> h=<sha> ps=<bytes>
      [f=<path> fh=<sha> fs=<bytes>] [w= ht=] [d=] [t=<title> a=<author>]
                                                  2.4: a link preview the sender made and uploaded
LPNO  s=c|p m=<hash>-<age> u=<url key>           2.4: the sender's plugin won't announce a preview of that link
```

- Unknown types and fields are ignored, and so is `tsm2` and later, so newer versions can add to the protocol. A command we send is at most 900 bytes; a received one above 2048 bytes is dropped before it is copied. Values are limited to `[A-Za-z0-9._,:-]`.
- **The sender's identity is never in the payload:** receivers take the invoker the server fills in. ServerQuery clients are ignored for `R` and `SYNC`. A channel reaction counts only from someone in our channel right now, a private one only from the partner of an open private chat and only for media seen in that chat.
- **PluginLink** keeps one queue per connection (presence before reactions before background work). Each command carries its own return code; no answer within about 3 s counts as not sent, and a late `Ok` is still delivered. A permission error marks the server as blocking plugin commands, and presence and reactions stay off there. Commands share the connection's `FloodGovernor` with chat posts.
- **Presence** (`PeerDirectory`): entering a channel starts an 800 ms settle time, then one `HELLO` with `rr=1` goes to the channel. Members answer with one `HI` after a random 150–900 ms (answers to several joiners merge). A member without an answer within 4 s (6 s for someone who just joined) counts as without TS Media; 2.1 and older can't answer and count the same. Private chats get one `HELLO` per partner at most once a minute; the server chat never asks anyone. Nothing is kept on disk. Turning presence off drops queued `HELLO`/`HI` and sends `BYE`. Every `HELLO`/`HI` with a `v=` from someone visible (not a ServerQuery client, not our own identity on another client) also emits `PeerDirectory::versionSeen` (2.3.4; untrusted, never for `BYE`), which feeds the updater's newer-version hint (below).
- **Reactions** (`ReactionStore`): one ordered set of emoji per reactor and media key (at most 10); `i=` lists every item with the six classic codes (`up heart lol wow sad fire`) it has, and `e=` carries the whole set as emoji wire codes (`1f923`, `2764-fe0f`) when it holds any other emoji, so older 2.2 builds still see the six. Pills are shown in the order the reactions first appeared, at most 20 different ones per media. A new `R` replaces a set, an empty set removes it. Your own clicks are applied at once, sent debounced, and taken back if they couldn't be sent. After entering a channel a `SYNC` asks the present members; each answers with its own reactions only, never anyone else's. `reactions.json` keeps at most 500 media and 100 reactors each for 30 days and is always saved within the 2 MB its loader accepts.
- **Reactions on messages** (2.3, `textreact.h`): TeamSpeak messages have no ids, so each client works one out from its own chat: `<hash>` is 16 hex digits of SHA-256 over the sender's unique ID (from the header's client link) and the message text, normalized so that what differs between clients doesn't count (only letters, digits and emoji, case-folded; TeamSpeak's emoticon codes left out, as text and as pictures, since icon packs and settings differ; spacing and line breaks left out). The time is when this client received it (the header's time and the day of its day lines). On the wire `<age>` is how many seconds ago the sender of the command received the message, so clocks and time zones don't matter: the receiver takes the message with that hash it received nearest to now − age, within 6 s. Repeats of the same text are told apart by their time (header times are whole seconds, so repeats less than about 2 s apart may share where a reaction lands). The rules, limits and debouncing are those of `R` and `SYNC`; a private reaction counts only on the reactor's own message outside the channel chat, or on ours in the private chat known to be with the reactor (anyone on the server can send `s=p`). After entering a channel, `TSYNC` names the newest messages of the channel chat by their hash and age. 2.2 builds ignore both types. The row is a picture of ours at the end of the message's block, after a line break of ours; both carry properties every other module skips, and a row that comes, changes or goes keeps what the reader looks at in place. `text-reactions.json` keeps at most 1000 messages for 30 days.
- **Link previews** (2.4, `src/linkpreview/`): when you send a chat message (channel or private chat) with a link to a YouTube video (https, or http as TeamSpeak links an address typed without a scheme) or an https link to a picture, GIF or video file, your plugin fetches it once, makes the preview (the YouTube thumbnail; a smaller copy of a picture; a GIF's first frame; a video's poster frame and duration) and uploads it, plus the file itself under the caps (pictures and GIFs within your automatic download limit, GIFs at most 8 MB, videos at most 25 MB, always within the upload limit), through Core's ordinary upload path as a quiet *background send*: the same folders (`<upload folder>/previews` for a preview on its own), SHA-256, flood governor and 2.3.2 server check (never a file info question on TeaSpeak), but no toast, no chat warning and no chat message. Then one `LP` goes to the same chat, naming the message like `TR` does. Receivers accept it only from the message's own sender (the invoker the server filled in must be the uid of the message found in that chat), never from ServerQuery clients, a channel `LP` only from someone in their channel for files in their channel, at most 10 per person per minute; one for a message not in their chat yet waits 15 s. The message is the nearest one within 60 s of the age the `LP` gives (its age is written when it is made, and a background command may wait in the transport behind presence, reactions or a flood pause). Accepted ones are kept in `link-previews.json` (at most 2000, four links per message, 90 days without use, 2 MB; cleared with *Clear cache*) and their files come from the TeamSpeak server through Core, checked against the announced SHA-256: the preview always, the file by the automatic download rules. Every `LP` field is checked (`linkpreview/announcement.h`): paths absolute without `..`, the preview a JPEG or PNG, the file's extension fitting its kind, hashes canonical, sizes within 2 MB (preview) and 100 MB (file), titles without control or bidi characters. The server chat has no `LP` (plugin commands can't address it). A job that ends without a preview sends one `LPNO` to the same chat (never for links refused by the rate limit or the queue, never at unload, after a setting went off, after leaving the channel or when the partner left), so each accepted job costs at most one command; the reason is only logged (the website's host, never the address). Receivers check `LPNO` exactly like `LP` (the message's own sender, LP's per-sender limit, waiting 15 s for its message) and keep it in memory only (256, 15 minutes).
- **Load link previews automatically** (2.4, `linkpreview/autoload.h`, `ChatLinkPreviews`): `linkstate::decide` gets one more input, a wait. A slot of our own message waits for our own sender pipeline (*Making the preview…*, also with the switch off; an 8 s grace covers the message showing before the pipeline has it) and shows the pipeline's download the moment its fetch is done (`SenderPipeline::OwnLink` records and `ownLinkChanged`; the click path's adoption), never switching to the stored `LP` during the session. A slot of someone else's message waits for the sender's preview while the sender makes them (`HELLO`/`HI` capability `l`, `PeerDirectory::capabilityState`) and is in our channel or private chat, for 30 s (YouTube), 45 s (pictures, GIFs) or 120 s (videos) after the sender's links before it (`autoload::SenderQueue`: the sender's pipeline makes one preview at a time across their messages and drops a job queued for 120 s), counted from the message's time, at most 120 s more than its own; an `LPNO`, the sender leaving or losing `l` ends it at once. While our question is out (a private partner nobody asked, someone whose `HI` said no `l` more than a minute ago: `PeerDirectory::recheckPartner`, a member who hasn't answered) it waits as *Checking for the sender's preview…*. Presence is one lookup for every chat kind (`autoload::PresenceMemo`, `ts3::uidPresence`: any client of that identity in our channel counts). A lost caps `HELLO` goes again like a `HELLO`. Otherwise, with the switch on, a slot on screen (the paint pass, ±400 px) loads from the website by itself: at most 2 at once over all chats and one per sender, a per-sender token bucket (6, then one per 10 s; a slot that has to wait its turn is held as a click card until a pass starts it, newest first), within `autoload::autoCap` (YouTube always; pictures and GIFs the automatic image limit; videos the video limit, or the image limit while that is 0; nothing but YouTube with data saver). The Fetcher stops before the body when the website announces more, and the card shows the size with **Load preview** (the limit when the size is unknown; *Too large* when even a click couldn't load it). A lower limit or a server's data saver stops a running automatic load (`ChatLinkPreviews::limitsChanged`, also from the menu and `/tsmedia datasaver`). A slot whose announcement *Clear cache* took (`PreviewStore::clearedEarlier`, in memory for the session) never loads by itself. A canceled fetch keeps a file it already put in place (the other `Fetcher` may have handed it out). Links already in `cache/links` show from there with no request (every link of a chat, so cards keep their final size). The queue runs from a child timer, never in a paint; a second child timer looks at visible waits once a second; both stop in `prepareShutdown`, which also lets go of the hub, the pipeline and the peer directory.
- **Link previews, how the pieces meet** (2.4): one message key everywhere: `textreactdoc::localKeyOf` over the chat document (`ChatTextReactions::keyOf` is that key with the chat's day lines, as the text index has it), so the hub resolves an `LP` to the same key the chat's cards look up in `PreviewStore::find` (which forgives a few seconds between the sender's echo and a receiver's header). A slot's card or media object carries its own properties, which `textreactdoc::identify` skips, so a link preview never changes a message's key or its text-reaction rows. One way to name a sender's files: `linkpreview::linkFor` (the hub's `requestFiles` and the chat's cards), so Core keeps one entry per file whoever asks first. The sender names the kind by the bytes it got, the chat by the address: pictures and GIFs are one family (`linkstate::kindFits`). A sender's preview whose main file fails, or whose preview fails while its full file waits for a click, gives the slot back to the website (an automatic load, or *Load preview*; `linkstate::serverFailed`). A website's file is a made-up link of the reserved server `tsmedia-web` (`linkstate::webLink`, only `Core::adoptLocalFile` makes one); a chat link naming that server is forged and ignored (`Core::ensure`, the chat's scan). Two `Fetcher`s, one per side: the sender pipeline's (it downloads into `cache/links` too and the maker copies from there; part names never collide) and the chat's click and automatic loads (`cache/links`). The chat never starts a request for a link the pipeline is fetching; it waits for that download. Both log through `linkpreview::usePluginLog` (the address tagged private). Every website request follows `netpolicy.h`; when the user's Windows settings name a proxy for the address (manual, setup script or WPAD, read with `WinHttpGetIEProxyConfigForCurrentUser` / `WinHttpGetProxyForUrl`), the request goes through it and the local DNS check and the connected-address check are skipped (the proxy resolves and connects), everything else stays. A failed fetch shows one neutral line (`linkstate::errorText`), the reason goes to the log. At unload, `PeerHub::prepareShutdown` stops the pipeline and its fetcher and `ChatLinkPreviews::prepareShutdown` the chat's, before the chat, `PeerHub` and Core go. *Clear cache* removes `cache/links` (Core) and `link-previews.json` (the hub); which links had a sender's preview stays known in memory until TeamSpeak restarts.

## Untrusted input

Anyone can post a `ts3file://` link with any parameters, or send a plugin command, so every value from the chat is treated as untrusted:

- `w` and `h` are clamped to 1–16384 and the aspect ratio to 1:8–8:1; `d` must not be negative.
- A BlurHash longer than 120 characters, or one that doesn't validate, is ignored.
- `pv` must be an absolute path without `..`, in the same channel, and must not point at the main file. A preview transfer above 5 MB is aborted.
- The 2.2 fields are accepted only in their exact form (table above); one hostile-input table drives the tests of every feature that reads them.
- Images above 80 megapixels are never decoded; the size is checked before decoding.
- Displayed names lose control and bidirectional-text characters, and file names are sanitised (`filenames::safeLocalFileName`) before they are used on disk.
- Programs, scripts and other file types Windows runs on double-click are never opened, only shown in Explorer.
- Plugin commands are parsed by `peerprotocol` field by field, rate-limited per sender and size-limited before anything is stored. In `R`, an `e=` wire code must be lower-case hex code points (at most 10 code points, 16 emoji per item), and only emoji of the built-in table are kept (others, from a newer version, are left out); a malformed `e=` (also one naming a key that isn't in `i=`) is ignored as a whole and `i=` counts.
- Emoji: only emoji of the built-in table become pictures, at most 400 per message, a few milliseconds of chat work per step.
- Replies: a quote line counts only when it parses completely (an arrow, the author's `client://` link or plain name, an optional time, an optional quoted snippet, nothing else; at most 600 characters, a name of 64 and a snippet of 240). A quote line with any other link is not a quote. Nothing in it is fetched or run, and finding its original only compares text, author and time.
- Link previews (2.4): only links that `linkpreview::classify` takes (YouTube videos, also http ones; https picture / GIF / video files) get a slot, at most 3 per message, never in TS Media's own lines or after a TS Media file link; a website is contacted on a click, by the sender for their own message, or automatically for links on screen without a sender-made preview (`Settings::autoLoadLinkPreviews`, within the automatic download limits, 2 at a time, one per sender, a per-sender budget). Titles and channel names lose control and bidirectional-text characters and are length-capped; a sender's preview is only taken from that message's sender, its paths are checked like `pv` and each file has a SHA-256.

## Updates

The update check is built only with `TSMEDIA_UPDATER=ON` (official releases). The manifest of the official repository's latest release (`tsmedia-update-v2.json`, fetched over HTTPS; the signed `tsmedia-update.json` that 2.2.0 reads is still verified when it is used) names the size and SHA-256 of each raw `.update` asset; the plugin builds every URL itself, follows redirects only to GitHub hosts, checks each file's PE machine and that its imports resolve in the running TeamSpeak, and installs by renaming the loaded DLL aside. A boot counter in `ts3plugin_init` rolls back a version that never finished starting. Everything else, including the manifest format, is in [updates](UPDATES.md).

- **Important updates** (2.3.4). After an automatic check with automatic checks on finds a newer version in `tsmedia-update-v2.json` (never after the fallback to `tsmedia-update.json`), the same worker job fetches that release's `TSMedia-<ver>-important.json` and reads it with `upd::readImportant` (the format 1 envelope, a daily signer, a format 3 payload with `important` and its dates; `updatemanifest.h`). `Updater::startAutoInstall` installs without a dialog only when the marker is valid, `sameRelease` with the v2 file, `autoInstallAllowed` (offered, the user's skip ignored, not on the `[auto] never` list that `onStarted` fills after a rollback or a manual downgrade) and the version has had fewer than 2 silent attempts. It then downloads against the marker's signed manifest; anything that goes wrong falls back to the normal offer, and a marker problem is only logged. `install` writes `[install] automatic=1` for the next start's line and never restarts TeamSpeak.
- **Newer-version hint** (2.3.4, `updatehint.h`). `PeerDirectory::versionSeen` reaches `Updater::notePeerVersion` (connected in `plugin.cpp`); `upd::PeerHints` decides (a strict version above everything the updater knows of, at most one major version ahead, monotonic, at most 2 per load), and `ts3::printInfoLink` prints the bold prefix, the text and a `[url=...]` link to the releases page with a `#tsmupd-<nonce>-<version>` fragment in one line into the channel tab. `ChatIntegration::filterOwnLink` takes the press, double click and release on such a link only in TS Media's own row (`layoutdoc::ownPrintLink`) when the updater's handler recognises this load's nonce, and the release runs `Updater::handleHintLink`, a manual check (`Origin::Chat`) that never fetches the marker. Anything else falls through to TeamSpeak, which opens the page.

## Threading and unloading

- TeamSpeak calls the plugin on its own threads; every callback is moved onto the GUI thread before it touches Qt objects. The static plugin-command callbacks hold a mutex from reading the hub pointer through queuing the call, so a callback never reaches a hub that is being deleted.
- Probing, hashing, compression, expensive image decodes, the editor's export, diagnostics and voice capture and encoding run on worker threads, so the GUI thread is never blocked for long.
- Emoji pictures are drawn on one low-priority worker thread with its own DirectWrite and Direct2D objects (a new emoji costs about 3 ms on Windows 11): the picker's, and the chat's HD emoji (a message is changed once its pictures are there). The GUI thread draws the few that reaction pills, menu icons and the input button need. Reply lines are drawn only for the lines on screen, right before the chat paints; they draw new emoji themselves for at most 16 ms per quarter second and leave the rest to the worker (shown as text until then), so replies quoting many new emoji can't hold up TeamSpeak's chat.
- A chat document TeamSpeak swaps out (and may show again) gets its quote lines and emoji back on unload too.
- TeamSpeak can unload the DLL while it keeps running. Nothing may outlive plugin shutdown: objects own their timers (delayed callbacks use `singleShotOwned()` from `src/ownedtimer.h`: a delayed `QTimer::singleShot` belongs to Qt's event dispatcher, not to its context object), worker threads are joined, Media Foundation players are shut down synchronously and the plugin's windows are closed.
- `ts3plugin_shutdown` runs in this order: `BYE` to everyone we said hello to and `reactions.json` written (`PeerHub::prepareShutdown`); the diagnostics hooks cleared; the updater (cancels a check or download, waits at most 1 s); every `tsmedia*` top-level window (the send window, the editor, the voice recorder, the viewer, the diagnostic info, the update dialogs, each waiting for its own worker); `ChatIntegration` (the voice controller first, which joins the recorder's worker and gives TeamSpeak's microphone back; then the reply lines and the HD emoji, which give every chat its text, smileys and layout back; then the inline players); leftover `tsmedia*` widgets inside TeamSpeak's chats; the server group helper; `PeerHub` (store, presence, transport); `Core` (joins the hash and transcode pools, removing a partial transcode); `emoji::shutdown` (joins the emoji worker, releases DirectWrite and Direct2D); `mf::shutdown`; and last the plugin log.
- Log lines tag their private values (`ts3::log(level, sch, "Uploaded %1", {ts3::file(path)})`). TeamSpeak's log gets plain text; the plugin's own log, `<data>/logs/tsmedia.log` (256 KB, one backup), keeps the tags so the diagnostic info can leave names out.
- Strings that end up in Qt or TeamSpeak state outliving the DLL (settings, style sheets, the clipboard, chat documents) are always heap-allocated through Qt, never `QStringLiteral` data stored in the DLL image. Otherwise TeamSpeak would crash on exit after the plugin was unloaded.
